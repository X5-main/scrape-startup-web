Today we're launching /kyc — the primitive that verifies the human or entity principal behind every autonomous business operating on Naïve. Government ID, selfie liveness, and compliance checks run through Naïve's KYC primitive as described in the verification guide, exposed as a runtime object that composes with /formation and /cards.

The problem: every regulated action requires a real principal

State filings, EIN applications, bank account openings, payment card issuance, e-signatures — every meaningful real-world action an agent takes is gated on someone who passed KYC. The state of Wyoming wants to know who's filing the LLC. The IRS wants to know who's responsible for the EIN. Card issuers want to know whose face matches the ID on the card.

For human-operated SaaS, this is a one-time onboarding flow. For autonomous businesses, it's the foundational primitive — and it's been the hardest one to build correctly.

The status quo is two bad options:

  1. Re-implement KYC from scratch on top of a raw provider like Persona, Onfido, or another vendor — and own all the PII handling, vault rotation, and audit logs yourself.
  2. Use the KYC built into a single vertical product (Mercury) — and re-verify every time you cross a product boundary.

Until now. /kyc runs the verification once, attaches it to an Employee, and lets every other primitive trust the result.

How /kyc works

The workflow is three steps:

  1. Start — naive verification start --members '[...]' with founder details. Naïve returns a hosted Naïve's KYC verification URL for the primary member and emails links to secondary members.
  2. Verify — each member opens the URL, uploads ID, completes identity verification, and consents. Naïve's KYC runs document checks and identity matching; the result writes back to Naïve.
  3. Compose — when all members pass (ready_for_formation: true), call /formation to form a Company, or /cards to issue a card as cardholder.

PII — government IDs, biometric vectors, addresses, dates of birth — is stored in an encrypted vault and hydrated only at submission time when an external system (state filing, IRS, card issuer) needs it. There is no Naïve API endpoint that returns vault contents to an agent or operator.

What /kyc verifies

Every verification produces a structured result the runtime can act on:

The cipFileUrl is the audit artifact every state filing system, EIN issuer, and bank wants to see. Naïve generates it from the verification and stores it on the Employee.

Two ways to start a verification: prompt or code

1. Natural language

The CLI returns the verification ID and the primary member's hosted URL. You hand the URL to the verifying party.

2. Code

The verification URL is single-use and is bound to the member. Re-issuing via naive verification resend <memberId> returns a fresh URL.

Watchlist screening, included

Every verification runs against OFAC, EU, UN, and HMT sanctions lists, plus PEP (politically-exposed persons) databases. Hits surface as structured WatchlistHit objects on the Employee, not as silent failures.

A watchlist hit doesn't auto-reject — it routes to manual review, where a human (you or Naïve compliance) can clear or escalate. This is the FATF-recommended pattern: detect, document, decide.

Revocation and consent

Every verification is consent-based, and consent is revocable. When a user calls revoke_verification_consent, Naïve schedules vault data for deletion in line with GDPR Article 17 and CCPA §1798.105. The Employee object retains the verification status flag for compliance audit trails, but the underlying PII is gone.

What you can build with /kyc

Verify a founder once, form ten companies — A single /kyc-passed Employee can act as principal across multiple /formation filings without re-verification. Useful for fleets of single-purpose companies.

Issue cards in real names with real liability — Compose /kyc with /cards so virtual cards are bound to a verified principal — not a generic "agent" account that will get rejected at higher-risk merchants.

Pass downstream KYC at banks and brokerages — The CIP file from /kyc follows the same structure many bank compliance teams use. You may share it with partners such as Mercury or Brex to reduce duplicate verification requests — acceptance is up to each institution.

Demonstrate beneficial ownership for FinCEN — Every Company formed via /formation ties to one or more /kyc-verified Employees. The result is a queryable, exportable beneficial ownership graph — exactly what the Corporate Transparency Act requires.

Run AML monitoring on agent-controlled accounts — Re-screen Employees against watchlists on a cadence. Surface hits to an operator before they become regulatory incidents.

Frequently Asked Questions
What is /kyc?+
/kyc is the Naïve primitive for verifying an Employee's identity. It captures government ID, runs a biometric liveness check, screens against AML and sanctions lists, and stores all PII in an encrypted vault. The verified Employee can then act as the principal of a /formation filing, the cardholder for /cards, or any other primitive that requires a real human signer behind the agent.
How does /kyc work?+
You run naive verification start with a members array containing each founder's name, email, ownership percentage, and role. Naïve generates a hosted Naïve's KYC verification URL for the primary member (returned in the response) and emails links to secondary members. Each member opens the URL in a browser and completes ID upload, selfie capture, and consent. Status updates can be polled via naive verification status.
Who provides the underlying KYC?+
Naïve's KYC primitive — the published verification guide describes hosted verification links, validation tokens, and member statuses. Naïve adds the Employee/Company runtime context and the ready_for_formation gate for formation.
How much does /kyc cost?+
Each verification is billed per-attempt. See the pricing page for current rates.
How is /kyc different from calling a KYC API directly?+
A raw vendor API gives you verification endpoints and dashboards for humans. /kyc is the Naïve primitive: members and ownership percentages attach to a Company, hosted verification links return through the documented flow, ready_for_formation gates /formation, and the same verification composes with /cards — without you building the orchestration layer.
What about FinCEN beneficial ownership and the EU AI Act?+
Every /kyc verification produces a CIP file (customer identification program) intended to support FinCEN CDD recordkeeping workflows. For EU AI Act compliance, /kyc provides an audit trail that a real human principal stood behind autonomous-business actions. Naïve does not advise on regulatory specifics — consult counsel for your obligations.
How do I get started with /kyc?+
Install the CLI with npm install -g @usenaive-sdk/cli, then run naive verification start --members '[{...}]' with founder details. Naïve returns a hosted Naïve's KYC URL for the primary member. Send the URL to the verifying party. Poll with naive verification status <id> until ready_for_formation is true. The full quickstart is at usenaive.ai/docs/getting-started/quickstart.
