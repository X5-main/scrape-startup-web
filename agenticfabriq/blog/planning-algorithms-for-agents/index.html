A Field Guide to Planning Algorithms for Agents

CoT, ToT, GoT, ReAct, PAL, and multi-stage planners — compared, stress-tested, and implemented.

Paulina Xu•April 16, 2026•22 min

Modern AI agents are only as reliable as their planners. Whether an agent is navigating the web, writing code, using tools, or orchestrating complex workflows, its planning algorithm determines how it reasons, explores, backtracks, and survives uncertainty.

And yet: developers often treat planning like “prompt engineering with extra steps.” It isn’t. Planning is an algorithmic choice — a topology — and different planning families behave radically differently once the world becomes messy, unpredictable, or tool-driven.

The distinction matters because the failure modes are structural, not stylistic. A linear planner cannot recover from a wrong first step no matter how good the model is, and a branching planner cannot avoid combinatorial cost no matter how clever the prompt. The shape of the reasoning process puts hard ceilings on what any underlying model can achieve. Picking the wrong topology is the kind of mistake no amount of prompt tuning will fix.

This field guide walks through the major planning paradigms — Chain-of-Thought (CoT), Tree-of-Thought (ToT), Graph-of-Thought (GoT), ReAct, PAL, and modern multi-stage planners — comparing how they perform under uncertainty, how they break, how they scale, and how to implement each one correctly.

It also integrates leading research from planning surveys, tool-use evaluations, hallucination studies, and long-horizon benchmarks including WebArena, SWE-Bench Pro, AgentBench, MINT, and PLANET-style suites.

Planning Families at a Glance

Every planning method corresponds to a different reasoning topology:

  • Chain-of-Thought (CoT) — a line
  • Tree-of-Thought (ToT) — a branching tree
  • Graph-of-Thought (GoT) — a general graph, can revisit states
  • ReAct — a line with tool feedback loops
  • PAL — a line guided by executable code
  • Multi-stage planners — a full pipeline (plan, act, reflect, repair)

This isn’t just conceptual — it changes everything about reliability. The topology determines two things that dominate real-world behavior: whether the planner can recover from a mistake, and whether it can ground its reasoning in feedback from the outside world. A line can do neither. A tree can recover but stays trapped inside the model’s own imagination. A loop with tool calls can ground but struggles to recover. Multi-stage planners are the first family that does both at once — which is exactly why they dominate the hardest benchmarks.

Chain-of-Thought (CoT): Linear, Elegant, and Fatally Overconfident

CoT is the simplest form of structured reasoning:

“Think step-by-step.”

The idea is deceptively powerful. By forcing the model to externalize its intermediate steps instead of jumping straight to an answer, CoT gives the model more tokens to compute over and a scaffold to keep its logic coherent. For a large class of single-shot reasoning problems, that scaffold is enough.

What it looks like

prompt = f"""
Solve the problem step by step.
Question: {task}
"""

Strengths

  • Great for short math, logic, and tightly scoped reasoning
  • Extremely cheap — a single model call, no orchestration
  • Very interpretable — the reasoning trace is the audit log

Behavior under uncertainty

Terrible. CoT assumes every intermediate step is correct; if the model makes a wrong early assumption, the rest of the chain collapses. There is no mechanism for the planner to notice it went wrong, because the only thing it can observe is its own prior reasoning — and that reasoning already encoded the mistake.

This is why CoT often fails on WebArena, SWE-Bench Pro, and any environment where the agent must interact or get feedback. The model commits to a path before it has the information needed to know whether the path is correct, and then dutifully follows it off a cliff.

Failure modes

  • Catastrophic cascade failures — one bad step poisons everything downstream
  • Hallucinated tool success (“Assuming the API call returned X…”)
  • No backtracking, no repair, no second opinion

Use it for

  • Math benchmarks (GSM8K, GSM-Hard)
  • Local reasoning that does not depend on external state
  • Preliminary plan sketching, before a more robust planner takes over

Tree-of-Thought (ToT): Branching Reasoning with Search

ToT explores multiple possible reasoning paths — a crucial advantage when uncertainty is high. Instead of committing to a single chain, the planner generates several candidate continuations at each step, scores them, and keeps the most promising ones. Combined with a search strategy like breadth-first search, depth-first search, or beam search, this lets the model look ahead and backtrack rather than barreling down the first line that occurs to it.

What it looks like

def expand_thoughts(node):
    return llm.generate(f"Expand this partial plan:\n{node}")

def evaluate(thought):
    return llm.generate(f"Rate the promise of this idea (0-10):\n{thought}")

# BFS or beam search over candidate thoughts

Strengths

  • Can backtrack when a branch turns out to be a dead end
  • Can explore contradictory hypotheses in parallel
  • Reduces dependence on a single “perfect” CoT

Behavior under uncertainty

Better than CoT, because the model hedges by exploring alternatives instead of betting everything on one chain. But there is a catch worth stating plainly: ToT only hedges over internal uncertainty. The branches it explores all live inside the model’s head. If the real source of uncertainty is the state of the outside world — what an API actually returns, what a page actually contains — searching harder over imagined possibilities does not help.

Major failure modes

  • Search over hallucinations — the model evaluates bad states as good, because the same model that generated the branch also scores it
  • Runaway branching costs — the number of model calls grows with branching factor times depth
  • Too many tool calls (catastrophic if tools affect real systems)

Use it for

  • Puzzles like Game of 24 and constraint satisfaction
  • Planning toy domains where the state space is fully internal
  • Tasks where “finding the right decomposition” matters more than executing it

Graph-of-Thought (GoT): Generalized ToT With Merging and Revisiting

GoT generalizes the tree into an arbitrary graph. Instead of each thought having exactly one parent, the planner can merge several lines of reasoning into a single synthesized state, reuse a sub-result computed earlier, or re-enter a previous “state” it had abandoned. Reasoning becomes a graph of interdependent steps rather than a strict hierarchy, which makes it strictly more expressive than ToT.

Strengths

  • Reduces duplicated work by reusing previously computed sub-results
  • Better at revisiting and correcting earlier assumptions
  • More expressive than ToT — it can aggregate and refine, not just branch

Failure modes

  • Can wander indefinitely without a clear termination condition
  • Extremely costly without pruning and deduplication
  • Evaluation heuristics (LLM scoring) may be unstable under noise — the same scoring fragility as ToT, now spread across a larger frontier

Use it for

  • Large search spaces with reusable structure
  • Problems with reusable submodules, where caching a sub-result pays off
  • Multi-dependency reasoning (e.g., plans that feed into each other)

ReAct: Reasoning + Acting in a Single Loop

ReAct changed the game by interleaving:

  • Thought — the model reasons about what to do next
  • Action — the model calls a tool
  • Observation — the model reads back what actually happened

This grounds reasoning in reality. The critical move is the observation step: after every action, the planner gets a fresh, external signal that it did not generate itself. That feedback is what breaks the closed loop of self-confirmation that dooms CoT and limits ToT. The model can reason to act, then act to reason — adjusting its plan based on what the world actually returned.

Example implementation

while not done:
    thought = llm(f"Thought: {history}")
    action = parse_action(thought)
    observation = tools[action.name](action.args)
    history.append((thought, action, observation))

Strengths

  • Low hallucination compared to CoT, because claims get checked against observations
  • Great for web tasks, QA, and fact retrieval
  • Handles uncertainty better because it checks its inferences against the world

Failure modes

  • Infinite loops when no progress is being made
  • Misinterpreting observations and acting on the wrong reading
  • Thrashing between tools (A, then B, then A, then B again)
  • Tool-overcalling — issuing far more calls than the task requires

Use it for

  • Real-world tasks that touch external state
  • Web navigation (WebArena, VisualWebArena)
  • Tool-using agents of almost any kind — this is the sensible default

PAL (Program-Aided Language Models): Code as the Plan

Here the LLM writes programs that actually solve the problem. Instead of asking the model to perform arithmetic or symbolic manipulation in its head — where it is unreliable — PAL asks the model to express the solution as code and offloads the actual computation to an interpreter. The model handles the part it is good at (translating a problem into a procedure) and the interpreter handles the part it is good at (executing that procedure exactly).

Example

# LLM output
def solve():
    x = compute_something()
    return x + 10

Then you run it in a sandbox.

Strengths

  • Ideal for math, algorithms, and data transformations
  • Very reliable for symbolic tasks where exactness matters
  • Scales extremely well for computation — interpreters do not make arithmetic mistakes the way LLMs do

Failure modes

  • Code with side effects you did not intend
  • Infinite loops that hang the executor
  • Unsafe filesystem or network access — you must sandbox

Use it for

  • GSM-HARD and other computation-heavy math
  • Algorithmic challenges
  • Data processing and transformation
  • Internal compute-heavy agents

Multi-Stage Planners: The Current Best Pattern for Long-Horizon Tasks

Multi-stage planners explicitly separate:

Plan, then act, then reflect, then repair.

The insight is to stop asking one model in one loop to do everything. Planning, execution, and criticism are different cognitive jobs with different failure modes, so you give each one its own role, prompt, and sometimes its own model. The result is a system that can both ground itself in feedback (like ReAct) and recover from structural mistakes (like ToT) — the two properties no single-family planner combines.

Often implemented with:

  • A planning model (large, reasoning-heavy)
  • An execution model (smaller, tool-aware, fast)
  • A critic / verifier model that can flag or veto bad steps

Example architecture

  1. Planner: break the task into subgoals
  2. Executor: ReAct-style execution per subgoal
  3. Reflector: find errors in what was produced
  4. Repair phase: rewrite subplans that failed
  5. Repeat until the task is complete or a budget is exhausted

Strengths

  • Strong results on WebArena
  • Strong results on SWE-Bench Pro relative to single-loop baselines
  • Most resilient to uncertainty
  • Supports memory, backtracking, and verification

Failure modes

  • If the plan is wrong, the entire system confidently does the wrong thing
  • More difficult to orchestrate, debug, and reason about
  • Requires role separation and process-level design, not just a clever prompt

Use it for

  • Enterprise agents
  • Web agents
  • Code agents
  • Any agent expected to run more than 20 steps

Comparative Behavior Under Uncertainty

PlannerUncertainty HandlingNotes
CoTVery poorNo revision, no backtracking
ToT/GoTModerateHedge via branching, but expensive and only over internal uncertainty
ReActGoodObservations ground hallucinations
PALExcellent (numeric/symbolic)Interpreter handles uncertainty
Multi-StageBestRe-planning plus reflection equals robustness

Uncertainty punishes overconfidence.

CoT is overconfident; ReAct, PAL, ToT, and multi-stage planners hedge. But notice they hedge against different kinds of uncertainty. ToT and GoT hedge against uncertainty in the model’s own reasoning. ReAct hedges against uncertainty about the state of the world. PAL eliminates uncertainty in computation entirely by delegating it to a deterministic interpreter. Multi-stage planners are the only family that addresses all three at once — which is precisely why they sit at the top of the column.

When Planners Fail Catastrophically With Tools

Tool use is where things get dangerous. Reasoning that stays inside the model is, at worst, wrong on paper. Reasoning that calls tools can delete a database, send an email, or charge a credit card. The cost of a planning mistake changes from “bad answer” to “bad action,” and each family fails in a characteristic way.

CoT

Catastrophic, because it assumes tool success without verifying. CoT will happily write “the record was deleted” into its reasoning and proceed as if it were true.

ReAct

Loops and misreads can cause endless tool calls or destructive API actions. The same feedback loop that grounds ReAct can, when misread, drive it to repeat a harmful action.

ToT/GoT

Search multiplies tool calls, so real-world side effects get multiplied along with them. Exploring ten branches that each write to a system means ten writes, not one.

PAL

Unsafe code can break sandboxes or hang indefinitely. The interpreter is exact, which is good for math and dangerous for anything with side effects.

Multi-stage

A single bad high-level plan leads to systematically harmful tool use, executed competently across every subgoal. The verifier role exists precisely to catch this before it happens.

The practical takeaway: separate read-only tools from side-effecting tools, and require explicit confirmation, a dry-run, or a critic sign-off before any action that mutates real state. Topology choice reduces the probability of a bad action; guardrails are what bound the blast radius when one slips through.

Scaling to Long-Horizon Tasks

Benchmarks show the brutal truth:

SWE-Bench Pro

  • Long-horizon software tasks remain hard — frontier models still resolve only a minority of issues, and well below their scores on the easier SWE-Bench Verified
  • Success requires long-term reasoning across many files, which is where multi-stage planning pulls ahead of single-shot approaches

WebArena / VisualWebArena

  • Agents must perform UI workflows spanning many dozens of steps
  • ReAct-style and multi-stage planners currently lead
  • CoT collapses, because it has no grounding

AgentBench / AgentBoard

  • Multi-phase and tool-grounded planning tend to outperform pure CoT/ToT on interactive, multi-step tasks

General takeaway

  • CoT: easy but fragile
  • ToT: smart but expensive
  • ReAct: good first choice
  • PAL: best for computation
  • Multi-stage: best for real agents in real systems

Benchmarking Frameworks To Reference

Useful benchmarks to evaluate against:

  • WebArena / VisualWebArena — long-horizon web tasks
  • SWE-Bench / SWE-Bench Pro — software planning
  • PLANET / planning benchmark collections — multi-domain planning
  • AgentBench, AgentBoard, MINT — agent ecosystems
  • HotpotQA, FEVER, BOLAA — QA with grounding
  • GSM8K, GSM-HARD — math planning
  • Cleanlab hallucination benchmarks — planning plus trust scoring

These benchmarks are designed to surface:

  • Planning brittleness
  • Action loops
  • Tool overuse
  • Uncertainty handling
  • Reasoning drift

One caution worth internalizing: a headline number on a leaderboard tells you almost nothing about whether a planner will work for your task. The benchmarks differ in horizon length, in how much they depend on tool feedback, and in whether the uncertainty is internal or environmental. Read the failure breakdowns, not just the top-line accuracy, and weight the benchmark whose structure most resembles your real workload.

Choosing a Planner: A Decision Framework

The families are not competitors so much as answers to different questions. Before reaching for the most powerful pattern, work through four questions about the task itself. The answers usually point at exactly one family.

1. Does the task touch external state?

If the agent must read from or write to the outside world — search the web, query a database, call an API — you need grounding, which means ReAct or a multi-stage planner with a ReAct executor. Pure CoT and ToT are off the table the moment correctness depends on something the model cannot see.

2. Is the hard part computation or decomposition?

If the difficulty is exact calculation, symbolic manipulation, or data transformation, reach for PAL and let the interpreter do the work. If the difficulty is finding the right way to break the problem apart, that favors ToT, GoT, or the planning stage of a multi-stage system.

3. How long is the horizon?

Short, self-contained reasoning lives comfortably in CoT. Anything that runs past roughly twenty steps needs explicit memory, verification, and repair — the structural guarantees only a multi-stage planner provides. The longer the horizon, the more a single un-checked mistake compounds.

4. What is the cost of being wrong?

Low-stakes, reversible tasks tolerate cheap planners. High-stakes or irreversible actions justify the orchestration overhead of a critic and a repair loop. Match the robustness of the planner to the cost of the failure it is meant to prevent — over-engineering a throwaway task wastes money, and under-engineering a consequential one wastes trust.

A useful default progression: start with ReAct, add PAL as a tool when computation appears, and graduate to a multi-stage planner only once the horizon, stakes, or failure rate demand it. Reach for ToT or GoT when you have a genuinely search-shaped problem and the budget to pay for it.

Implementation Guides for Each Planning Method

CoT

Use when: you want interpretability and simplicity.

Implementation:

  • Provide 1–3 CoT examples
  • Add a “verify your answer” post-check
  • Avoid for tool use

ToT

Implementation:

  • Implement BFS or beam search
  • Limit branching to 2–3 candidates
  • Use LLM heuristics to rate states
  • Add guards to avoid expanding hallucinated paths

GoT

Implementation:

  • Store states in a graph
  • Compare new states via embeddings for deduplication
  • Add memory replay plus pruning heuristics

ReAct

Implementation:

  • Wrap all observations in <obs> tags so the model never confuses them with its own output
  • Add a loop counter and a hard step budget
  • Include a “stop if repeating actions” rule to break thrashing
  • Add a validate_action() function before calling a tool

PAL

Implementation:

  • Sandbox all code
  • Set timeouts
  • Use a pure-Python environment
  • Define allowed imports and safe APIs
  • Use unit tests to evaluate generated code

Multi-stage

Implementation:

  • Write three system prompts: Planner, Executor, Critic
  • Define a JSON schema for plans
  • Add a repair loop
  • Add trust scoring so the critic can veto steps
  • Maintain memory across subgoals
  • Add a global timeout plus a step budget

Turning This Into Actual Code

Nice, this is the fun part. Let’s turn those planning patterns into actual, useable code.

I’ll assume:

  • Python 3.10+
  • A generic call_llm(prompt: str, system: str | None = None) -> str you can wire to OpenAI, Anthropic, etc.
  • A tool registry pattern for ReAct and multi-stage.
  • No external deps beyond the standard library (you can layer your own framework on top).

You can drop all of this into a single planning.py and adapt. The code is deliberately framework-agnostic: the same skeletons map cleanly onto LangChain, LangGraph, or a bespoke runtime once you decide where you want orchestration to live.

def register_tool(tool: Tool) -> None:
    TOOLS[tool.name] = tool

def call_tool(name: str, args: Dict[str, Any]) -> Any:
    if name not in TOOLS:
        raise ValueError(f"Unknown tool: {name}")
    return TOOLS[name].func(args)

1. Chain-of-Thought (CoT)

Simple, linear “think step-by-step” reasoning.

# cot_planner.py
from typing import Optional
from planning_core import call_llm
import textwrap

COT_SYSTEM_PROMPT = "You are a helpful assistant that solves problems step by step."

def cot_solve(question: str,
              few_shot_examples: Optional[str] = None,
              verify: bool = True) -> str:
    """
    Basic Chain-of-Thought planner.
    - question: the user problem
    - few_shot_examples: optional CoT examples to condition behavior
    - verify: whether to ask the model to double-check its own answer
    """
    examples_block = few_shot_examples or ""

    prompt = textwrap.dedent(f"""
    {examples_block}

    Now solve the following problem step by step.

    Question:
    {question}

    Show your reasoning as 'Thought:' lines and provide a final answer as:
    'Final Answer: <answer here>'
    """)

    raw = call_llm(prompt, system=COT_SYSTEM_PROMPT)

    if not verify:
        return raw

    verify_prompt = textwrap.dedent(f"""
    You previously produced this solution:

    {raw}

    Double-check whether the final answer is correct.
    If you find an error, provide a corrected 'Final Answer' and updated reasoning.
    Otherwise, confirm that the original final answer is correct.
    """)

    verified = call_llm(verify_prompt, system=COT_SYSTEM_PROMPT)
    return verified

Note that the optional verify pass is the cheapest reliability upgrade in this entire guide: a second self-check call catches a meaningful share of arithmetic and logic slips for the cost of one extra model call. It is not a substitute for grounding, but for pure-reasoning tasks it is almost always worth it.

2. Tree-of-Thought (ToT): Beam Search Over Reasoning Paths

Minimal ToT implementation with beam search over candidate thoughts.

# tot_planner.py
from dataclasses import dataclass
from typing import List
from planning_core import call_llm
import heapq
import textwrap

@dataclass
class Thought:
    text: str
    score: float

TOT_SYSTEM = "You are a deliberate problem solver that explores multiple reasoning paths."

def expand_thought(question: str, partial: str, num_candidates: int = 3) -> List[str]:
    """
    Ask the LLM to propose several next-step continuations.
    """
    prompt = textwrap.dedent(f"""
    You are exploring ways to solve this problem:

    Question:
    {question}

    Current partial reasoning:
    {partial}

    Propose {num_candidates} different next-step continuations of this reasoning.
    Number them as:
    1) ...
    2) ...
    etc.
    """)
    resp = call_llm(prompt, system=TOT_SYSTEM)

    # naive parse: lines starting with "1)" / "2)" etc.
    lines = [l.strip() for l in resp.splitlines() if l.strip()]
    candidates: List[str] = []
    for l in lines:
        if l[0].isdigit() and ")" in l[:3]:
            candidates.append(l.split(")", 1)[1].strip())
    return candidates[:num_candidates]

def score_thought(question: str, reasoning: str) -> float:
    """
    Ask the LLM to rate how promising this partial reasoning is.
    """
    prompt = textwrap.dedent(f"""
    Question:
    {question}

    Partial reasoning:
    {reasoning}

    Rate how promising this reasoning is for solving the problem.
    Respond with a single number between 0 and 10.
    """)
    resp = call_llm(prompt, system=TOT_SYSTEM)
    try:
        return float(resp.strip().split()[0])
    except Exception:
        return 0.0

def tot_solve(question: str,
              max_depth: int = 5,
              beam_width: int = 3) -> str:
    """
    Simple Tree-of-Thought beam search.
    - Keeps top-k (beam_width) partial reasoning paths at each depth
    - At the end, asks the LLM to finalize the best reasoning into an answer
    """
    # Start with an empty thought
    start = Thought(text="", score=0.0)
    frontier: List[Thought] = [start]

    for depth in range(max_depth):
        new_frontier: List[Thought] = []
        for t in frontier:
            candidates = expand_thought(question, t.text)
            for c in candidates:
                combined = (t.text + "\n" + c).strip()
                s = score_thought(question, combined)
                new_frontier.append(Thought(text=combined, score=s))

        # keep top beam_width by score
        frontier = heapq.nlargest(beam_width, new_frontier, key=lambda x: x.score)
        if not frontier:
            break

    # Use the best thought to produce final answer
    best = max(frontier, key=lambda x: x.score)
    final_prompt = textwrap.dedent(f"""
    Question:
    {question}

    Use the following reasoning to produce a final answer:
    {best.text}

    Provide the final answer as:
    'Final Answer: <answer>'
    """)
    final = call_llm(final_prompt, system=TOT_SYSTEM)
    return final

3. Graph-of-Thought (GoT): Reuse and Revisiting States

A lightweight GoT implementation: it stores visited states and avoids recomputing similar ones. This is more of a template than a full research-grade system, but it shows the structure.

# got_planner.py
from dataclasses import dataclass
from typing import Dict, List, Set
from planning_core import call_llm
import hashlib
import textwrap

@dataclass
class Node:
    reasoning: str
    score: float

GOT_SYSTEM = "You are a problem solver that can revisit and refine partial reasoning steps."

def hash_state(reasoning: str) -> str:
    return hashlib.sha256(reasoning.encode("utf-8")).hexdigest()

def got_expand(question: str, node: Node, num_candidates: int = 3) -> List[Node]:
    prompt = textwrap.dedent(f"""
    Question:
    {question}

    Current reasoning:
    {node.reasoning}

    Propose {num_candidates} ways to extend or refine this reasoning.
    Number them as 1), 2), etc.
    """)
    resp = call_llm(prompt, system=GOT_SYSTEM)

    lines = [l.strip() for l in resp.splitlines() if l.strip()]
    children: List[Node] = []
    for l in lines:
        if l[0].isdigit() and ")" in l[:3]:
            reasoning = l.split(")", 1)[1].strip()
            score_prompt = textwrap.dedent(f"""
            Question:
            {question}

            Partial reasoning:
            {reasoning}

            Rate how promising this reasoning is (0-10). Only output the number.
            """)
            s_raw = call_llm(score_prompt, system=GOT_SYSTEM)
            try:
                s = float(s_raw.strip().split()[0])
            except Exception:
                s = 0.0
            children.append(Node(reasoning=reasoning, score=s))
    return children

def got_solve(question: str,
              iterations: int = 10,
              max_open: int = 20) -> str:
    """
    Simple Graph-of-Thought search:
    - maintains an "open list" of promising nodes
    - reuses visited reasoning states by hashing
    - iteratively expands high-score nodes
    """
    start = Node(reasoning="", score=0.0)
    open_list: List[Node] = [start]
    visited: Set[str] = set()

    for _ in range(iterations):
        # sort open_list by score descending
        open_list.sort(key=lambda n: n.score, reverse=True)
        open_list = open_list[:max_open]
        if not open_list:
            break

        node = open_list.pop(0)
        state_id = hash_state(node.reasoning)
        if state_id in visited:
            continue
        visited.add(state_id)

        children = got_expand(question, node)
        open_list.extend(children)

    if not open_list:
        best = start
    else:
        best = max(open_list, key=lambda n: n.score)

    final_prompt = textwrap.dedent(f"""
    Question:
    {question}

    Use the following reasoning (and refine it if needed) to produce a final answer:
    {best.reasoning}

    Provide the final answer as:
    'Final Answer: <answer>'
    """)
    final = call_llm(final_prompt, system=GOT_SYSTEM)
    return final

4. ReAct: Thought → Action → Observation Loop

This is a real skeleton you can drop into a tool-using agent.

# react_planner.py
import json
from typing import Any, Dict, List, Tuple
from planning_core import call_llm, call_tool, Tool, register_tool
import textwrap

REACT_SYSTEM = "You are an agent that reasons and acts using tools. Follow the Thought/Action/Observation format."

def format_history(history: List[Tuple[str, str, str]]) -> str:
    """
    History is a list of (thought, action, observation).
    """
    lines = []
    for i, (thought, action, obs) in enumerate(history, start=1):
        lines.append(f"Step {i}:")
        lines.append(f"Thought: {thought}")
        lines.append(f"Action: {action}")
        lines.append(f"Observation: {obs}")
        lines.append("")
    return "\n".join(lines)

def parse_action(line: str) -> Tuple[str, Dict[str, Any]]:
    """
    Expect something like:
        Action: search(query="python logging")
    We'll parse the tool name and args via a crude parse; you will likely want
    to tighten this with a structured format (e.g., JSON).
    """
    if not line.lower().startswith("action:"):
        raise ValueError("No Action: prefix found.")
    content = line.split(":", 1)[1].strip()
    # e.g. search(query="python logging")
    name, rest = content.split("(", 1)
    name = name.strip()
    args_str = rest.rsplit(")", 1)[0]
    # naive parse: treat as JSON-ish
    # Better: force the model to output JSON.
    try:
        args = json.loads(args_str)
    except Exception:
        args = {"raw": args_str}
    return name, args

def react_solve(question: str,
                max_steps: int = 10) -> str:
    """
    Core ReAct loop.
    """
    history: List[Tuple[str, str, str]] = []

    for step in range(max_steps):
        history_text = format_history(history)
        prompt = textwrap.dedent(f"""
        You are solving the following task:

        Question:
        {question}

        You must follow this strict format:

        Thought: <your reasoning>
        Action: <tool_name(args_as_JSON)>

        After each action, you will receive an Observation.
        Continue until you have enough information, then output:

        Thought: ...
        Action: finish(answer="<final answer here>")

        Here is the history so far:
        {history_text}
        """)
        resp = call_llm(prompt, system=REACT_SYSTEM)

        # find the last "Thought:" and "Action:" lines
        thought_line = ""
        action_line = ""
        for line in resp.splitlines():
            line = line.strip()
            if line.lower().startswith("thought:"):
                thought_line = line.split(":", 1)[1].strip()
            elif line.lower().startswith("action:"):
                action_line = line

        if not action_line:
            raise RuntimeError(f"No Action produced by LLM:\n{resp}")

        tool_name, args = parse_action(action_line)

        if tool_name == "finish":
            answer = args.get("answer", "")
            return answer

        try:
            raw_obs = call_tool(tool_name, args)
            observation = str(raw_obs)
        except Exception as e:
            observation = f"Tool error: {e}"

        history.append((thought_line, action_line, observation))

    raise RuntimeError("Max ReAct steps reached without finish().")

You can register tools like:

# tools_example.py
from planning_core import Tool, register_tool

def search_tool(args):
    query = args["query"]
    # call your search API here
    return f"[fake search results for: {query}]"

register_tool(Tool(
    name="search",
    description="Search the web.",
    schema={"type": "object", "properties": {"query": {"type": "string"}}},
    func=search_tool,
))

The crude regex-style parser here is fine for a demo, but in production you should force the model to emit structured JSON for its actions — through native tool-calling or a constrained-decoding library — so that parse_action never has to guess. A malformed action that silently falls back to {"raw": ...} is a subtle bug waiting to happen.

5. PAL: Program-Aided Language Models (Python Sandbox)

We let the LLM write a function and run it in a sandboxed namespace.

# pal_planner.py
from typing import Any, Dict
from planning_core import call_llm
import textwrap
import traceback

PAL_SYSTEM = "You write correct, pure Python functions to solve problems. Avoid side effects."

def pal_generate_code(question: str) -> str:
    prompt = textwrap.dedent(f"""
    You are a Python coding assistant.

    Write a single Python function 'solve()' that returns the answer to the problem below.
    The function should not read or write files or access the network.

    Problem:
    {question}

    Only output valid Python code. Do not wrap it in backticks.
    """)
    code = call_llm(prompt, system=PAL_SYSTEM)
    return code

def pal_execute(code: str, timeout_sec: int = 5) -> Any:
    """
    Execute generated code in a restricted namespace.
    This is a minimal sandbox - tighten for production.
    """
    # Very minimal sandbox - in production, restrict builtins harder.
    safe_globals: Dict[str, Any] = {
        "__builtins__": {
            "range": range,
            "len": len,
            "min": min,
            "max": max,
            "sum": sum,
            "abs": abs,
        }
    }
    local_vars: Dict[str, Any] = {}

    try:
        exec(code, safe_globals, local_vars)
    except Exception:
        raise RuntimeError(f"Error executing code:\n{traceback.format_exc()}")

    if "solve" not in local_vars:
        raise RuntimeError("No solve() function defined in code.")

    solve_fn = local_vars["solve"]
    # You can wrap this in a timeout via multiprocessing / threads if you want.
    result = solve_fn()
    return result

def pal_solve(question: str) -> Any:
    code = pal_generate_code(question)
    result = pal_execute(code)
    return result

Treat the restricted-builtins trick above as a speed bump, not a wall. A determined model can still reach dangerous capabilities through attribute traversal, and an infinite loop will hang the process regardless of which builtins you allow. For anything facing untrusted input, run generated code in a real isolation boundary — a separate process with a hard wall-clock timeout, a container, or a microVM — and never inside your main interpreter.

6. Multi-Stage Planner: Plan → Execute (ReAct) → Critic → Repair

Here’s a minimal but real multi-stage orchestration:

# multistage_planner.py
from dataclasses import dataclass
from typing import Any, Dict, List
from planning_core import call_llm, call_tool
from react_planner import react_solve  # reuse ReAct for execution
import json
import textwrap

PLANNER_SYSTEM = "You are a senior planner that breaks tasks into safe, coherent steps."
CRITIC_SYSTEM = "You are a strict critic that finds flaws in plans or results."

@dataclass
class PlanStep:
    id: int
    description: str

def make_plan(task: str, max_steps: int = 8) -> List[PlanStep]:
    prompt = textwrap.dedent(f"""
    You are planning a solution for this task:

    {task}

    Break the solution into at most {max_steps} high-level steps.
    Each step should be a short imperative phrase, like:
    "Collect user requirements"
    "Query the database"
    "Summarize findings"

    Respond as a JSON list of objects with fields:
    - id: integer step number starting at 1
    - description: string

    Example:
    [
      {{"id": 1, "description": "Read the input data"}},
      {{"id": 2, "description": "Filter invalid records"}},
      ...
    ]
    """)
    resp = call_llm(prompt, system=PLANNER_SYSTEM)
    try:
        data = json.loads(resp)
    except Exception:
        raise RuntimeError(f"Planner returned invalid JSON:\n{resp}")
    return [PlanStep(id=s["id"], description=s["description"]) for s in data]

def critic_review(task: str, plan: List[PlanStep], result: str) -> str:
    steps_text = "\n".join(f"{s.id}. {s.description}" for s in plan)
    prompt = textwrap.dedent(f"""
    Task:
    {task}

    Executed plan:
    {steps_text}

    Result:
    {result}

    As a critic, identify any flaws, safety issues, or missing steps.
    Then answer in JSON with:
    - "verdict": "ok" or "needs_repair"
    - "comment": explanation
    """)
    resp = call_llm(prompt, system=CRITIC_SYSTEM)
    return resp

def repair_plan(task: str, plan: List[PlanStep], critic_resp: str) -> List[PlanStep]:
    steps_text = "\n".join(f"{s.id}. {s.description}" for s in plan)
    prompt = textwrap.dedent(f"""
    Task:
    {task}

    Current plan:
    {steps_text}

    Critic feedback:
    {critic_resp}

    Based on the critic's feedback, repair or improve the plan.
    Respond with a new JSON list in the same format as before.
    """)
    resp = call_llm(prompt, system=PLANNER_SYSTEM)
    data = json.loads(resp)
    return [PlanStep(id=s["id"], description=s["description"]) for s in data]

def multistage_solve(task: str,
                     max_replans: int = 2) -> str:
    """
    Multi-stage planner:
    1. Plan
    2. Execute (here: reuse react_solve per subtask)
    3. Critic review
    4. Optionally repair + re-execute
    """
    plan = make_plan(task)

    for attempt in range(max_replans + 1):
        # naive execution: join plan step descriptions into a single question for ReAct
        # In a serious system, you'd execute each step individually and maintain state.
        execution_prompt = textwrap.dedent(f"""
        You must follow this plan:
        {chr(10).join(f"{s.id}. {s.description}" for s in plan)}

        Solve the overall task step by step using tools, then provide a final answer.
        """)
        result = react_solve(execution_prompt, max_steps=12)

        critic_json = critic_review(task, plan, result)
        try:
            critic = json.loads(critic_json)
        except Exception:
            # If critic is broken, just return the result
            return result

        if critic.get("verdict") == "ok":
            return result

        # Otherwise, repair and retry
        plan = repair_plan(task, plan, critic_json)

    # If we exhaust re-plans, return the last result anyway (and log)
    return result

Two upgrades turn this skeleton into something production-grade. First, execute each subgoal individually and thread state between them, rather than collapsing the whole plan into one ReAct call — that is what lets the critic localize a failure to a specific step instead of the entire run. Second, give the critic real teeth: let it gate side-effecting actions, not just review the final result after the damage is done.

Observability: Seeing What Your Planner Actually Did

Every planner above produces a structured trace — thoughts, actions, observations, scores, verdicts. That trace is the single most valuable artifact for debugging an agent, and most teams throw it away. If you cannot reconstruct why the agent took a step, you cannot fix the planner that produced it.

The pragmatic move is to instrument each planning stage as a span in a tracing system, attaching the prompt, the raw model output, the parsed action, and the observation to each one. A vendor-neutral standard like OpenTelemetry works well here, and it is increasingly the substrate that agent-tracing tools build on. The payoff shows up the first time an agent fails in production: instead of squinting at a wall of logs, you open a trace and watch the exact branch where reasoning drifted, the tool call that returned garbage, or the critic verdict that was overruled.

What is worth capturing for every run:

  • The full prompt and raw response at each step, not just the parsed result
  • Every tool call with its arguments, latency, and outcome — success, error, or timeout
  • Step counts and token spend, so runaway branching or looping is visible immediately
  • Critic verdicts and repair decisions, so you can audit when and why the plan changed

Treat the trace as a first-class output. The planner is the skeleton; observability is the X-ray that tells you which bone broke.

Final Recommendations (Developer-Friendly)

  • Use CoT for quick, cheap, interpretable reasoning.
  • Use ReAct as your default for any tool-based agent.
  • Use PAL for math, data structures, transformations, and structured logic.
  • Use ToT/GoT when exploration matters more than speed.
  • Use multi-stage planning for anything serious:
    • enterprise
    • workflow agents
    • autonomous data agents
    • coding agents
    • web automation
    • long-horizon tasks

And do not treat these as mutually exclusive. The strongest production agents are hybrids: a multi-stage planner whose executor runs ReAct, calls PAL as a tool when a subgoal turns numeric, and falls back to plain CoT for the trivial steps that do not deserve the overhead. Choose the topology per task, not per project.

Because in the real world, planning isn’t just reasoning — it’s orchestration. And the planner you choose is the skeleton your entire agent stands on.
