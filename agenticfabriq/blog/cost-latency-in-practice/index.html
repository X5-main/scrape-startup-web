Optimizing Agent Cost & Latency in Practice (LangChain, LangGraph, AutoGen Versions)

Framework-by-framework patterns for cutting agent cost and latency in LangChain, LangGraph, and AutoGen.

Paulina Xu•April 20, 2026•15 min
EngineeringFrameworksPerformance

Why Optimize?

Most agent developers eventually hit the same wall: your agent works, but it’s slow, expensive, and behaves just differently enough under cheaper models to break production expectations. Good news — you don’t need specialized infrastructure to fix this. With a bit of architectural thinking (and the right pattern per framework), you can often:

  • cut inference cost substantially, frequently in the range of cutting it by half or more
  • reduce end-to-end latency by a multiple, not just a few percent
  • maintain behavior consistency across model tiers
  • introduce confidence-based routing
  • automatically avoid unnecessary RAG fetches

Those numbers depend heavily on your workload — a chatty support bot and a multi-step research agent will see very different savings — but the levers are the same, and they compound. This post shows you exactly how to implement these optimizations in LangChain, LangGraph, and AutoGen, with working code for each.

The reason the wins are so large is that most naive agents do the expensive thing every time. They send the full conversation and every retrieved document to the most capable (and most costly) model on every single turn, whether or not the task warrants it. A planning step that just needs to enumerate three subtasks is paying frontier-model prices. A simple greeting triggers a vector search and a 4,000-token context stuff. The optimization is mostly about doing the cheap thing first and the expensive thing only when it actually earns its keep.

Agent workloads have two extremes:

  1. Heavyweight thinking (planning, global reasoning, decomposition)
  2. High-stakes execution (final answers, tool actions, user-visible responses)

The trick is mapping these to two model classes:

  • Fast, cheap model (planning, summarization, compression, “should we RAG?”)
  • Accurate, expensive model (final generation, tool usage, multi-step synthesis)

This is the same idea behind model cascades: route the easy fraction of work to a small model and reserve the large model for the cases that genuinely need it. The cheap model does not have to be perfect — it only has to be good enough to plan, triage, and compress, which are tasks where a smaller model is often surprisingly competitive.

Pair this with:

  • Lazy evaluation (only run RAG when needed)
  • Context compression (give the slow model a lighter meal)
  • Caching (don’t re-plan what you’ve planned before)
  • Confidence routing (don’t always trust the first pass)

Now let’s translate that into framework-specific patterns.

1. LangChain: Fast Planner + Slow Executor + Caching + Context Optimization

LangChain’s strength here is composition. Every model, prompt, and helper is a Runnable, so you can pipe them together with the | operator and swap pieces in and out without rewiring the whole agent. We’ll build the optimized flow one Runnable at a time and then compose them.

1.1. Setup: Fast + Slow Models

from langchain_openai import ChatOpenAI
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.runnables import RunnableLambda
from langchain_core.output_parsers import StrOutputParser

# Fast, cheap model (planning, summaries, compression)
fast_llm = ChatOpenAI(
    model="gpt-4o-mini",
    temperature=0,
)

# Slow, high-quality model (final execution, user-visible answers)
slow_llm = ChatOpenAI(
    model="gpt-4.1",
    temperature=0,
)

Note that prompt templates now live in langchain_core.prompts rather than the older langchain.prompts path. Keeping imports on the langchain_core namespace is the safest choice across recent versions.

1.2. Planning Chain (Fast Model)

The planner only enumerates steps — it never produces the final answer — so it is a perfect job for the cheap model. Keeping the planner output structured and terse also keeps the executor prompt small later on.

planner_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a planner. Break the user task into clear steps. No final answer."),
    ("user", "{question}")
])

planner_chain = planner_prompt | fast_llm | StrOutputParser()

1.3. Lazy RAG + Context Compression (Fast Model)

Assume you already have a retriever, e.g. a vector store.

from langchain_core.documents import Document

def compress_docs(docs: list[Document]) -> str:
    if not docs:
        return ""
    joined = "\n\n".join(d.page_content for d in docs)
    prompt = f"Summarize the following context in <= 5 bullet points:\n\n{joined}"
    return (fast_llm | StrOutputParser()).invoke(prompt)

def maybe_retrieve(question: str, retriever, threshold: float = 0.5) -> list[Document]:
    """
    Ask the model if we need RAG at all. Lazy evaluation.
    """
    judge_prompt = f"""
    Question: {question}
    Do we need to look up external documents to answer this?
    Respond with a single word: yes or no.
    """
    resp: str = (fast_llm | StrOutputParser()).invoke(judge_prompt)
    if "yes" in resp.lower():
        # retriever.invoke() is the modern Runnable call;
        # get_relevant_documents() has been deprecated.
        return retriever.invoke(question)
    return []

Two things are happening here. The maybe_retrieve guard turns retrieval into a decision rather than a reflex: a one-token “yes/no” from the cheap model is far cheaper than an embedding query plus a context-stuffed generation, and on many turns the honest answer is “no.” The compress_docs step then shrinks whatever you do retrieve into a handful of bullets, so the expensive model reads a paragraph instead of a dossier. Note that retrievers are Runnables now, so you call retriever.invoke(question) rather than the deprecated get_relevant_documents.

To wrap this in a Runnable:

def lazy_context_fn(inputs: dict):
    question = inputs["question"]
    retriever = inputs["retriever"]
    docs = maybe_retrieve(question, retriever)
    compressed = compress_docs(docs)
    return {"compressed_context": compressed}

lazy_context = RunnableLambda(lazy_context_fn)

1.4. Execution Chain (Slow Model, with Planner + Compressed Context)

executor_prompt = ChatPromptTemplate.from_messages([
    ("system", "You are a precise, careful assistant. Follow the plan and use context."),
    ("user", "Question: {question}\n\nPlan:\n{plan}\n\nContext:\n{compressed_context}")
])

executor_chain = executor_prompt | slow_llm | StrOutputParser()

By the time the slow model runs, the hard thinking is already done: it has a plan to follow and a compressed context to ground it. That means the expensive call is short, focused, and predictable — which is exactly when a frontier model is worth paying for.

1.5. Wiring It Together + Caching Reasoning

LangChain ships built-in caching too — you can set a global LLM cache via set_llm_cache to deduplicate identical model calls. Here we keep it explicit and just memoize the planner step so repeated questions skip planning entirely.

from functools import lru_cache

@lru_cache(maxsize=1024)
def cached_plan(question: str) -> str:
    return planner_chain.invoke({"question": question})

def optimized_agent_lc(question: str, retriever):
    plan = cached_plan(question)
    ctx = lazy_context.invoke({"question": question, "retriever": retriever})
    answer = executor_chain.invoke({
        "question": question,
        "plan": plan,
        "compressed_context": ctx["compressed_context"],
    })
    return {
        "plan": plan,
        "answer": answer,
    }

One caveat worth flagging: lru_cache keys on the exact question string, so it only helps with verbatim repeats. For production you usually want a semantic cache (embed the question, match on similarity) or LangChain’s own cache backends, which can persist across processes. Either way, the principle holds: don’t re-plan what you’ve already planned.

This gives you:

  • fast planning (cached)
  • lazy RAG
  • compressed context
  • slow, accurate executor

All within LangChain.

2. LangGraph: Routing by Stage and Optimizing Execution Paths

The LangChain version is linear: plan, maybe-retrieve, execute, done. That’s fine until you want to branch — retry on a weak answer, ask for clarification, or skip a stage entirely. LangGraph is purpose-built for exactly that control flow, modeling the agent as an explicit state machine where each node reads and updates a shared state object.

  • Node 1: planning (fast model)
  • Node 2: maybe-RAG (fast model)
  • Node 3: compressed-context execution (slow model)
  • Optional Node: retry/repair if low confidence

2.1. Define State

from typing import TypedDict, Optional, Any

class AgentState(TypedDict):
    question: str
    plan: Optional[str]
    compressed_context: Optional[str]
    answer: Optional[str]
    confidence: Optional[float]
    retriever: Any  # store a handle/identifier

Use Any (capital A, imported from typing) rather than the lowercase builtin any, which is a function, not a type.

2.2. Nodes

Each node is a plain function that takes the state and returns the keys it wants to update. LangGraph merges those updates back into the state, so a node only has to return what it changes.

Planner Node (fast)

def planner_node(state: AgentState) -> AgentState:
    plan = planner_chain.invoke({"question": state["question"]})
    return {**state, "plan": plan}

Lazy RAG Node (fast, may do nothing)

def context_node(state: AgentState) -> AgentState:
    docs = maybe_retrieve(state["question"], state["retriever"])
    compressed = compress_docs(docs)
    return {**state, "compressed_context": compressed}

Executor Node (slow)

Add confidence estimation inline:

import json

def execution_node(state: AgentState) -> AgentState:
    prompt = f"""
    Question: {state['question']}
    Plan:
    {state['plan']}
    Context:
    {state['compressed_context']}

    Respond JSON:
    {{
        "answer": "<answer>",
        "confidence": 0-1
    }}
    """
    resp = (slow_llm | StrOutputParser()).invoke(prompt)
    data = json.loads(resp)
    return {**state, "answer": data["answer"], "confidence": data["confidence"]}

Asking the model to self-report a confidence score in the same call is cheap, but free-form JSON parsing is brittle — a stray code fence or trailing comment will break json.loads. In production, prefer structured outputs: bind a schema with slow_llm.with_structured_output(...) (or a library like Instructor) so the model is constrained to valid JSON and you skip the manual parse entirely.

2.3. Router Node Based on Confidence

def router_node(state: AgentState) -> str:
    conf = state.get("confidence") or 0.0
    if conf > 0.8:
        return "done"
    if 0.5 < conf <= 0.8:
        return "clarify"
    return "retry"

This is the payoff of the graph structure: the expensive executor runs once, and the cheap routing decision determines whether you stop, ask for clarification, or retry. High-confidence answers exit immediately instead of paying for extra passes.

2.4. Build the Graph

from langgraph.graph import StateGraph, START, END

workflow = StateGraph(AgentState)

workflow.add_node("plan", planner_node)
workflow.add_node("context", context_node)
workflow.add_node("execute", execution_node)
workflow.add_node("clarify", lambda s: {**s, "answer": "I need clarification."})
workflow.add_node("retry", planner_node)  # trivial retry; you can customize

workflow.add_edge(START, "plan")
workflow.add_edge("plan", "context")
workflow.add_edge("context", "execute")
workflow.add_conditional_edges(
    "execute",
    router_node,
    {
        "done": END,
        "clarify": "clarify",
        "retry": "retry",
    },
)

graph = workflow.compile()

Using add_edge(START, "plan") is the current idiom for setting the entry point; the older set_entry_point still works but the explicit START node reads more clearly alongside END. Note that the retry branch loops back through planning, so you’ll want a guard (a retry counter in state, or a recursion limit) to avoid an infinite loop on a persistently low-confidence answer.

2.5. Invoke

result = graph.invoke({
    "question": "Analyze these error logs and recommend actions.",
    "plan": None,
    "compressed_context": None,
    "answer": None,
    "confidence": None,
    "retriever": your_retriever,
})

print(result["answer"], result["confidence"])

LangGraph now encodes:

  • model mixing
  • lazy context
  • confidence-based routing
  • room for retries

…with a proper state machine.

3. AutoGen: Planner–Executor Multi-Agent with Cost/Latency Optimization

AutoGen is great for multi-agent setups, which map naturally to:

  • Planner agent (fast model)
  • Executor agent (slow model)
  • Optional Critic agent (fast model for validation)

A note on versions before we dive in. AutoGen has two API generations. The original conversational API — from autogen import AssistantAgent with a dict llm_config and synchronous generate_reply — is shown below because it is the most concise way to express the pattern, and it is still maintained (now also under the community AG2 fork). The newer Microsoft autogen-agentchat package replaces this with a per-agent model_client (e.g. OpenAIChatCompletionClient) and async methods like on_messages / run. The optimization pattern is identical in both; only the call surface differs.

3.1. Basic Setup

from autogen import AssistantAgent, UserProxyAgent

planner = AssistantAgent(
    name="planner",
    system_message="You are a planner. Break tasks into steps. No final answers.",
    llm_config={"model": "gpt-4o-mini", "temperature": 0},
)

executor = AssistantAgent(
    name="executor",
    system_message="You execute plans precisely and safely.",
    llm_config={"model": "gpt-4.1", "temperature": 0},
)

critic = AssistantAgent(
    name="critic",
    system_message="You check answer quality and rate confidence 0-1.",
    llm_config={"model": "gpt-4o-mini", "temperature": 0},
)

user = UserProxyAgent(name="user")

The key cost lever is in those llm_config blocks: the planner and critic run on the cheap model, and only the executor pays for the frontier one. Two of the three agents in this team are inexpensive.

3.2. RAG Helper (Lazy Evaluation)

You can keep this outside AutoGen, or wrap as a tool.

def lazy_rag(question, retriever):
    docs = maybe_retrieve(question, retriever)
    return compress_docs(docs)

3.3. Orchestrating Planner → Executor → Critic

import json

def optimized_autogen_agent(question: str, retriever):
    # 1) Planner: fast model
    plan_msg = planner.generate_reply(
        messages=[{"role": "user", "content": question}]
    )
    plan = plan_msg  # plaintext

    # 2) Lazy context
    compressed_context = lazy_rag(question, retriever)

    # 3) Executor: slow model with plan + compressed context
    exec_prompt = f"""
    Question: {question}
    Plan:
    {plan}
    Compressed context:
    {compressed_context}

    Provide a JSON object with:
    - answer: string
    """
    exec_msg = executor.generate_reply(
        messages=[{"role": "user", "content": exec_prompt}]
    )
    answer_data = json.loads(exec_msg)
    answer = answer_data["answer"]

    # 4) Critic: fast model for confidence
    critic_prompt = f"""
    Evaluate the following answer for factual accuracy and appropriateness.
    Question: {question}
    Answer: {answer}

    Respond JSON:
    {{
        "confidence": 0-1,
        "comment": "..."
    }}
    """
    critic_msg = critic.generate_reply(
        messages=[{"role": "user", "content": critic_prompt}]
    )
    critic_data = json.loads(critic_msg)

    return {
        "plan": plan,
        "answer": answer,
        "confidence": critic_data["confidence"],
        "critic_comment": critic_data["comment"],
    }

Notice that this orchestrates the agents by hand rather than handing them to a group chat. That is deliberate: a free-flowing multi-agent conversation can balloon token usage as agents talk past each other, so for a cost-sensitive pipeline an explicit planner → executor → critic call order is usually cheaper and more predictable. The same parsing caveat from LangGraph applies — guard the json.loads calls or use a structured-output wrapper.

This AutoGen version gives you:

  • fast planner agent
  • slow executor agent
  • fast critic agent for quality & confidence
  • lazy RAG + compressed context

You can also use AutoGen’s tools mechanism to:

  • expose a retriever as a tool
  • expose a compress_context tool
  • record logs & metrics per agent

Measuring the Wins

Optimizations you can’t measure tend to quietly regress. Before you tune anything, capture a baseline so you know what you actually saved — and so the next person who touches the agent can tell whether their change helped or hurt. Three numbers matter most: total tokens (split into prompt and completion, since they price differently), wall-clock latency per request, and the fraction of requests that hit the expensive model versus the cheap one. That last ratio is the real scoreboard for everything in this post; if your slow model is still firing on every turn, none of the routing is working.

A lightweight wrapper around each model call is enough to start. The point is to attribute cost to a stage — planning, retrieval, execution, critique — so you can see where the money goes.

import time
from collections import defaultdict

stats = defaultdict(lambda: {"calls": 0, "prompt_tokens": 0, "completion_tokens": 0, "seconds": 0.0})

def track(stage: str, llm, prompt: str) -> str:
    start = time.perf_counter()
    resp = llm.invoke(prompt)
    elapsed = time.perf_counter() - start

    usage = resp.response_metadata.get("token_usage", {})
    s = stats[stage]
    s["calls"] += 1
    s["prompt_tokens"] += usage.get("prompt_tokens", 0)
    s["completion_tokens"] += usage.get("completion_tokens", 0)
    s["seconds"] += elapsed
    return resp.content

For anything beyond a quick experiment, lean on real tracing. LangChain and LangGraph emit traces to LangSmith out of the box, and OpenTelemetry gives you a vendor-neutral way to ship spans for every model and tool call into whatever observability backend you already run. The instrumentation is the same regardless of framework; what you’re watching for is always the same pair of curves — cost per request trending down, and the expensive-model hit rate staying low without quality falling off.

Which Framework Should You Use?

All three implement the same playbook — fast planner, slow executor, lazy RAG, compressed context, confidence routing — so the choice is mostly about the shape of your problem rather than which one is “faster.”

LangChain is best when you want:

  • composable chains
  • simple architecture
  • quick iteration

LangGraph is best when you want:

  • control flow
  • retries, fallback routing
  • production stability

AutoGen is best when you want:

  • multi-agent collaboration
  • planner/executor/critic patterns
  • tool-agent ecosystems

A pragmatic path for many teams is to start in LangChain to validate the pattern quickly, then graduate the same flow into LangGraph once you need retries, branching, and durable state — the planner, executor, and helpers carry over almost unchanged. Reach for AutoGen when the problem is genuinely a team of specialists collaborating, rather than a single pipeline with stages.

You don’t need specialized infrastructure to make agents fast and affordable — just the right pattern for your framework: a fast planner, a slow executor, lazy RAG, compressed context, and confidence-based routing.
