How to Optimize Agent Cost and Latency Without Breaking Behavior

Practical engineering patterns for faster, cheaper, and more stable LLM agents — without breaking their behavior.

Paulina Xu•April 23, 2026•12 min
EngineeringPerformanceCost
IntroductionModel MixingLazy EvaluationReasoning CacheContext WindowCompress ToolsFull Pipeline

Introduction: The Hardest Part of Agent Optimization

Agent developers quickly hit a wall:

Your agent works… but it’s too slow and too expensive.

And the moment you optimize it, the behavior breaks:

  • plans become shallow
  • reasoning collapses
  • tool calls loop forever
  • incorrect answers increase
  • subtle safety problems appear

This is the central tension of production agents. The naive fixes — a smaller model here, a truncated prompt there, a hard cap on reasoning steps — almost always cost you accuracy or reliability somewhere downstream, and the regression is rarely obvious until a user trips over it. Cost and latency are easy to measure; behavior is not. That asymmetry is exactly why teams over-optimize the numbers they can see and quietly break the ones they can’t.

Optimizing agents without changing their behavior is an engineering discipline, not a prompt hack. The patterns below share a single principle: spend expensive compute only where it changes the outcome, and spend cheap compute everywhere else. Done well, you can hold accuracy roughly constant while cutting cost and latency substantially — and in several cases, trimming context bloat actually makes the agent more stable, not less.

In this post, we’ll cover:

  • model mixing (fast planning, slow execution)
  • lazy evaluation
  • reasoning caching
  • context window optimization
  • tool/result compression
  • with real code templates and architectural patterns for robust, stable performance.

Every code sample uses the OpenAI Python SDK, but the patterns are provider-agnostic — they map cleanly onto Anthropic, open-weight models served locally, or any mix of the three. Treat the model names as placeholders you swap for whatever you run today.

Model Mixing: Use Fast Models for Thought, Slow Models for Action

The most powerful cost/latency optimization is splitting planning and execution across different models:

  • fast model (GPT-4o-mini, Claude Haiku, Qwen 2.5 7B): used for planning, idea generation, candidate actions
  • slow model (GPT-4.1, Claude Sonnet, Claude Opus): used only for final decisions, tool calls, or irreversible actions

This mirrors how search engines, compilers, and planners work: cheap exploration to high-precision execution. A query planner explores many candidate query plans cheaply and commits to one expensive execution; a compiler runs fast heuristic passes before the costly optimization passes. Agents benefit from the same shape because planning is forgiving — a slightly clumsy plan still gets corrected downstream — while execution is unforgiving, since a single wrong tool call can be irreversible.

The economics are stark. A small model often costs an order of magnitude less per token than a frontier model, so moving the high-volume, low-stakes planning chatter onto the cheap model is usually the single largest line-item reduction you can make without touching the agent’s answers at all.

Implementation Architecture

User → Fast Model (planning) → Slow Model (execution) → Tools

Example Code: Two-Model Pipeline

from openai import OpenAI
client = OpenAI()

def fast_plan(question):
    res = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "Draft a high-level plan. No tool calls."},
            {"role": "user", "content": question}
        ]
    )
    return res.choices[0].message.content

def slow_execute(plan):
    res = client.chat.completions.create(
        model="gpt-4.1",
        messages=[
            {"role": "system", "content": "Using the plan, execute the task with high precision."},
            {"role": "user", "content": plan}
        ]
    )
    return res.choices[0].message.content

Usage

plan = fast_plan("Summarize these documents and find contradictions.")
result = slow_execute(plan)

Where Model Mixing Breaks Behavior

  • if the fast model hallucinates incorrect plan steps
  • if the slow model interprets the plan too literally
  • if planner and executor personas differ (use consistent system prompts)

The literal-interpretation failure is the sneakiest one. A frontier executor will faithfully carry out whatever the plan says, including its mistakes, because it has been told to trust the plan. If the fast planner invents a step, the slow model won’t second-guess it — it will execute it perfectly. The fix is not a smarter executor; it is a gate between the two stages.

Solution: always validate the plan before executing:

def validate_plan(plan):
    res = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "Is the plan complete, safe, and executable? Respond true/false."},
            {"role": "user", "content": plan}
        ]
    )
    return "true" in res.choices[0].message.content.lower()

Because validation runs on the cheap model, the gate is essentially free relative to one frontier call. When it fails, re-plan rather than execute — a short retry loop on the fast model is far cheaper than letting a bad plan reach a tool that writes to your database.

Tuning the Split: When to Escalate

Model mixing is not all-or-nothing. The most robust setups route per step rather than per request, escalating to the slow model only when a step crosses a complexity or risk threshold. A useful rule of thumb:

  • read-only and reversible steps stay on the fast model
  • writes, payments, deletions, and anything user-facing escalate to the slow model
  • steps the fast model flags as low-confidence escalate automatically

This keeps the frontier model on the critical path only where its precision actually earns its cost, and it gives you a single dial — the escalation threshold — to trade accuracy against spend without rewriting the agent.

Lazy Evaluation: Don’t Evaluate Unless You Need It

Many agents evaluate:

  • every retrieved document
  • every tool call
  • every clarification step
  • every previous message

even when none of it is necessary.

Lazy evaluation means: only compute the next step when you truly need it. Borrowed from functional programming, the idea is to defer work until its result is actually demanded — and in agents, a surprising amount of work is never demanded at all. A question the model already knows the answer to does not need retrieval; a request that is already unambiguous does not need a clarifying turn. Each of those skipped steps is a saved round-trip, and round-trips dominate latency far more than tokens do.

Technique A — Conditional Document Retrieval

def maybe_retrieve(question):
    needs_rag_prompt = f"""
Do we need external documents to answer this: "{question}"?
Respond yes or no.
"""
    res = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": needs_rag_prompt}]
    )
    if "yes" in res.choices[0].message.content.lower():
        return rag_search(question)  # expensive fetch
    return []

The gating call here is cheap and fast; the retrieval it guards is neither. Skipping a vector search plus the tokens those documents would have added to every subsequent prompt is a compounding win, because the saved context is paid for not once but on every loop the documents would otherwise have ridden along in.

Technique B — Delayed Tool Calls

Instead of calling tools immediately, ask the model:

def should_call_tool(plan):
    res = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[{"role": "user", "content": f"Is a tool call required? {plan}"}]
    )
    return "yes" in res.choices[0].message.content.lower()

Technique C — Stop Asking for Clarifications Automatically

Agents often ask useless clarifying questions (token tax).

Use a cheap model to detect whether a clarification is necessary.

Each unnecessary clarification doubles the latency the user feels and adds a full conversational turn to every later prompt. A one-line gate on the fast model — does this request have enough information to act on, yes or no — removes most of them while still letting the genuinely ambiguous cases through.

A Note on Where Lazy Evaluation Breaks

The risk with every gate above is the same: the cheap model says “no” when the answer was really “yes,” and the agent confidently produces a wrong answer it could have looked up. Lazy evaluation should fail toward doing the work, not skipping it. When the gating model is uncertain, default to retrieving, calling the tool, or asking the question — the cost of a false skip is a broken answer, which is exactly the behavior regression these optimizations are supposed to avoid.

Cache Reasoning Steps (Save 40–80% of Token Costs)

Most tasks repeat reasoning: explanations, schemas, parsing, summarization, context analysis.

You can cache the reasoning, not just final answers. The same document gets summarized again and again across requests; the same schema gets re-derived; the same context gets re-analyzed. Each repetition is a full inference you already paid for once. Caching the intermediate result turns that recurring cost into a one-time cost — and across a busy agent, intermediate reasoning is far more repetitive than the final answers users actually see.

Implementation: Reasoning Cache

import hashlib
import json

reasoning_cache = {}

def cache_key(prompt):
    return hashlib.sha256(prompt.encode()).hexdigest()

def cached_reason(prompt, model="gpt-4o-mini"):
    key = cache_key(prompt)
    if key in reasoning_cache:
        return reasoning_cache[key]
    res = client.chat.completions.create(
        model=model,
        messages=[{"role": "user", "content": prompt}]
    )
    answer = res.choices[0].message.content
    reasoning_cache[key] = answer
    return answer

The in-memory dict shown here is the simplest possible store; in production you would swap it for Redis or any shared cache so the savings persist across processes and restarts. Note that the SHA-256 key requires an exact prompt match, which is both a feature and a limit — it never returns a stale answer for a different prompt, but it also misses semantically identical prompts that differ by a whitespace. For near-duplicate prompts, key off an embedding-based similarity bucket instead of the raw string.

Example: Cache summaries & analyses

summary = cached_reason("Summarize document X")
analysis = cached_reason("Extract entities from document X")

Application Caching vs. Native Prompt Caching

The cache above is an application-level cache: you store and reuse the model’s output yourself. It is distinct from, and complementary to, the native prompt caching that the major providers now offer at the API layer. Native caching reuses the model’s internal computation over a repeated prompt prefix — on the OpenAI API it activates automatically for prompts beyond roughly a thousand tokens with no code change, while Anthropic exposes explicit cache breakpoints you mark on the request.

The two work best together. Native caching rewards you for keeping your large, static content — system prompt, tool definitions, few-shot examples — at the front of the prompt and your variable, user-specific content at the end, so the stable prefix stays cacheable. Application caching, meanwhile, eliminates the call entirely for reasoning you have already produced. Use the provider cache to make each call cheaper, and your own cache to make fewer calls.

Avoid caching final answers for user queries (reduces personalization). Cache structural reasoning, not decision outputs.

Context Window Optimization: Don’t Send Everything

Large prompts mean higher latency, more cost, and higher hallucination risk.

The last point matters most for behavior. Beyond a certain size, more context does not make an agent smarter — it makes it more distractible. Irrelevant passages compete for the model’s attention, dilute the genuinely useful tokens, and push the most important facts toward the middle of a long prompt where models attend to them least. Trimming context is therefore not only a cost lever; it is often an accuracy lever.

The key patterns:

  • relevance filtering
  • semantic dedupe
  • chunk scoring
  • context compression
  • key-value memory instead of raw transcripts

A. Semantic Chunk Scoring

def get_relevant_chunks(query, chunks, top_k=5):
    scored = [(chunk, similarity(query, chunk)) for chunk in chunks]
    return [c for c, _ in sorted(scored, key=lambda x: x[1], reverse=True)[:top_k]]

Here similarity is typically cosine similarity between embedding vectors for the query and each chunk. Tune top_k empirically: too low and you starve the model of context it needed, too high and you reintroduce the very bloat you set out to remove. Starting around five chunks and adjusting against an evaluation set is a reasonable default.

B. Compress all context before sending

def compress_context(context):
    res = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "Summarize in 5 bullet points. No details, only facts."},
            {"role": "user", "content": context}
        ]
    )
    return res.choices[0].message.content

Use compressed summaries instead of raw documents.

Compression trades a cheap extra call for a much smaller payload on the expensive call — usually a clear win, since the fast model summarizes once while the slow model would have re-read the full text on every loop. The caveat is lossiness: a summary that drops the one figure or clause the task hinged on will quietly produce a wrong answer. Keep verbatim anything the downstream step must quote or compute on, and compress only the surrounding narrative.

C. Drop Conversation History

Replace full transcript with:

  • Last 1–2 user messages
  • Agent’s last reply
  • Memory summary
  • Task plan

Almost always enough.

Replaying the entire transcript on every turn is the most common source of slow, expensive agents, because the prompt grows without bound as the conversation continues. A rolling summary plus the most recent turns gives the model the continuity it needs at a flat, predictable token cost — and as a bonus, it keeps the prompt’s stable prefix intact so native prompt caching keeps paying off.

Compress Tools & Responses for Faster Loops

If your tools return:

  • huge JSON
  • full logs
  • raw markdown
  • complete HTML
  • verbose error messages

…you’re paying unnecessary tokens every loop.

Tool output is uniquely expensive because it lands back in the prompt and then rides along on every subsequent step of the loop. A single bloated API response does not cost you once — it costs you on every turn until it scrolls out of context. That makes tool results the highest-leverage place to compress.

You want:

  • compressed tool output
  • safe structured summaries
  • model-ready representations

Example: Tool Output Compressor

def compress_tool_result(raw):
    # Compress using a fast LLM
    res = client.chat.completions.create(
        model="gpt-4o-mini",
        messages=[
            {"role": "system", "content": "Compress tool output to essential data. No fluff."},
            {"role": "user", "content": raw}
        ]
    )
    return res.choices[0].message.content

Before reaching for an LLM, ask whether plain code can do the job. Most of the worst offenders — pretty-printed JSON, HTML wrappers, stack-trace noise, repeated boilerplate — can be stripped deterministically with a parser or a few lines of filtering, with zero added latency and no risk of the summarizer dropping a field. Reserve the LLM compressor for genuinely unstructured output where rules do not suffice.

Add structured constraints

def compress_json(raw_json):
    prompt = f"""
Given this JSON, output a minimal JSON keeping only:
- IDs
- titles
- status
- essential fields
Compress, remove null or unused fields.
JSON:
{raw_json}
"""
    return cached_reason(prompt)

Routing this through cached_reason means an identical tool response is only ever compressed once — the reasoning cache and the tool compressor reinforce each other. For anything mission-critical, validate the compressed JSON against a schema before trusting it, so a malformed summary fails loudly instead of silently corrupting the next step.

Pipeline: Tools → Compressor → Executor

Tool → Compressor → LLM Execution → Next Step

You reduce token size 5–20x in real systems.

Putting It All Together: A Full Optimization Pipeline

Each pattern helps on its own, but they compound when composed. Fast planning shrinks the work; lazy evaluation removes work entirely; compression shrinks what survives; caching ensures nothing is paid for twice. The pipeline below wires them into a single function:

def optimized_agent(question):
    # 1. Fast plan
    plan = fast_plan(question)

    # 2. Lazy RAG
    docs = maybe_retrieve(question)

    # 3. Context compression
    compressed_docs = [compress_context(d) for d in docs]

    # 4. Slow executor with compressed context
    final = slow_execute(
        f"Plan:\n{plan}\n\nCompressed documents:\n{compressed_docs}"
    )
    return final

Notice what the slow, expensive model actually sees: a compact plan and a handful of compressed bullet summaries — never the raw question-to-answer firehose. The frontier call runs on the smallest, most relevant prompt the rest of the pipeline could produce, which is precisely where its cost is justified.

This pipeline achieves:

  • 30–70% latency reduction
  • 40–85% cost reduction
  • near-identical accuracy
  • higher stability through reduced context bloat

Treat those ranges as what is achievable, not what is guaranteed — the actual numbers depend heavily on your task mix, how repetitive your reasoning is, and how bloated your starting prompts were. The discipline that makes them safe is measurement: hold an evaluation set fixed and watch accuracy as you turn each optimization on. If a change moves cost down and accuracy stays flat, keep it. If accuracy slips, you have found the boundary — back off the threshold rather than abandoning the pattern.

Optimizing agents without changing their behavior is an engineering discipline, not a prompt hack — model mixing, lazy evaluation, reasoning caching, and context compression let you ship faster, cheaper, and more stable agents.
